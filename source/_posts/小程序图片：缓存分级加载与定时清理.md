# 小程序图片：缓存、分级加载与定时清理

我最近迷上了自己折腾微信小程序，从零搭了一个小项目练手。功能写完、兴冲冲上线给几个朋友试用之后，才发现一个被我严重低估的问题：**图片**。

本地调试时图都在，感觉丝般顺滑；一上真机、走云存储，卡顿、白屏、流量蹭蹭涨全来了。翻了翻自己写的代码才意识到，图片这块几乎没做任何处理——原图直接传、原图直接显示、也不清理。于是我花了一段时间把这摊子收拾干净，摸索出一套通用的图片处理思路。本文就当我的踩坑笔记，把「上传压缩、本地缓存、分级加载、定时清理」这四件事讲清楚，方案不依赖任何特定项目，你照搬就能用。

---

## 一、我踩到的那些坑

小程序里的图片，是个很隐蔽的体验杀手：

- 云存储的图片用 `cloud://` fileID 表示，每次展示都要运行时去解析/签发，有网络开销
- 相册、时间线一屏十几张图，**重复下载**，又慢又费用户流量
- 手机存储空间有限，**只进不出**迟早把缓存撑爆
- 上传原图动辄几 MB，**不压缩**上传慢，还白白占云存储额度

所以一个像样的图片方案，至少得解决四件事：**压缩上传、本地缓存秒开、分级加载、定时清理**。下面我一件一件说。

---

## 二、整体思路

我把整条链路理成这样一条线：

```
上传 ──> 压缩 ──> 云存储(cloud:// fileID)
                        │
展示 <── 自封装图片组件 ── 本地文件缓存(USER_DATA_PATH/imgcache)
                        │           │
                  命中直接渲染   未命中→下载落盘(LRU)
                        │
相册/列表 ── prefetch 预加载下一屏 ──> 提前进缓存
```

我给自己定的一个原则：**展示源只用 `cloud://`**，业务代码里不要到处散落 `wx.cloud` 调用；所有图片都走一个统一的图片工具函数处理。这样后面要加缓存、要加分级，只动一处就行。

## 三、上传：先压缩，再控制并发

### 3.1 单张上传（带压缩）

```ts
async function upload(filePath: string, scene: string, onProgress?: (p: number) => void): Promise<string> {
  const compressed = await compress(filePath)        // 先压缩
  const cloudPath = buildCloudPath(scene, compressed) // 按目录规则生成路径
  const task: any = wx.cloud.uploadFile({ cloudPath, filePath: compressed })
  if (onProgress && task.onProgressUpdate) {
    task.onProgressUpdate((res: any) => onProgress(res.progress || 0))
  }
  const up: any = await task
  return up.fileID
}
```

### 3.2 自动压缩（我只压大的）

```ts
async function compress(filePath: string): Promise<string> {
  const stat = /* 取文件体积 */
  if (stat > 1.5 * 1024 * 1024) {
    const res = await new Promise<any>((resolve) => {
      wx.compressImage({ src: filePath, quality: 75, success: resolve, fail: () => resolve({ tempFilePath: filePath }) })
    })
    return (res && res.tempFilePath) || filePath
  }
  return filePath
}
```

> 我的经验：**只对大于 1.5MB 的图压缩**，小图直接传，避免无谓的画质损失；压缩万一失败就回退原图，别让上传卡住。

### 3.3 批量上传（控制并发，避免被限流）

```ts

```

> 云开发对单连接有限流，我实测**并发 2** 是个稳妥值，既快又不会触发限流报错。

### 3.4 目录规则

```ts
const DIR: Record<string, string> = {
  avatar: 'avatars', photo: 'photos', record: 'records'
}
// cloudPath = {dir}/{userKey}/{时间戳}-{随机}.{ext}
```

按「场景 + 用户」分目录，后面不管是按用户清理，还是按场景定位，都方便。

### 3.5 一次上传，顺手出多档图

这里有个我后来才意识到的点：上面 `upload()` 传的是「压缩后的原图」，可原图在列表里根本用不上。列表一屏十几张，全用原图既费流量又拖首屏；点开大图看原图，大部分用户也只是「扫一眼」，未必需要全分辨率。

所以我改成上传时**顺手再生成两档小图**，三份一起存云存储、一起返回 fileID：

```ts
// 缩略图：列表用，短边 200px，质量 70
async function makeThumb(filePath: string): Promise<string> {
  const info = await new Promise<any>((r) => wx.getImageInfo({ src: filePath, success: r, fail: () => r({} }) })
  const short = Math.min(info.width || 1080, info.height || 1080)
  const scale = short > 0 ? 200 / short : 1
  const res = await new Promise<any>((r) =>
    wx.compressImage({
      src: filePath, quality: 70,
      compressedWidth: Math.round((info.width || 200) * scale),
      compressedHeight: Math.round((info.height || 200) * scale),
      success: r, fail: () => r({ tempFilePath: filePath })
    })
  )
  return res.tempFilePath || filePath
}

// 预览图：点开查看用，短边 1080px，质量 80
async function makePreview(filePath: string): Promise<string> {
  const info = await new Promise<any>((r) => wx.getImageInfo({ src: filePath, success: r, fail: () => r({} }) })
  const short = Math.min(info.width || 1080, info.height || 1080)
  const scale = short > 0 ? 1080 / short : 1
  const res = await new Promise<any>((r) =>
    wx.compressImage({
      src: filePath, quality: 80,
      compressedWidth: Math.round((info.width || 1080) * scale),
      compressedHeight: Math.round((info.height || 1080) * scale),
      success: r, fail: () => r({ tempFilePath: filePath })
    })
  )
  return res.tempFilePath || filePath
}

// 一次上传，三份存储：原图 + 缩略图 + 预览图
async function uploadWithSizes(filePath: string, scene: string): Promise<{
  origin: string; thumb: string; preview: string
}> {
  const compressed = await compress(filePath)
  const [origin, thumbFile, previewFile] = await Promise.all([
    upload(compressed, scene),
    makeThumb(compressed).then((f) => upload(f, scene)),
    makePreview(compressed).then((f) => upload(f, scene))
  ])
  return { origin, thumb: thumbFile, preview: previewFile }
}
```

三档分别是：**`thumb` 列表缩略图(~200px)、`preview` 点开预览图(~1080px)、`origin` 原图**。业务数据里同时存这三个 fileID，不同场景取不同的用。生成靠 `wx.compressImage` 指定输出尺寸，纯客户端就能做，不依赖服务端。

> 为什么上传时就出齐：列表、查看、原图三种尺寸是确定的，早生成一次存好，展示时直接拿现成的，比临时再去压缩/裁剪省事得多。

### 3.6 三档分别用在哪，为什么这么分

三档不是拍脑袋定的，是照着「用户实际怎么看图」来切的。先一句话原则：**列表用 `thumb`、点开用 `preview`、原图只有用户主动点「保存原图」才拉到相册**。

```
thumb  (缩略图 ~200px)   ──> 列表九宫格 / 头像，几十张同时刷，省流量秒开
  │
preview(预览图 ~1080px)   ──> 点开查看，够清晰又不费流量，是用户 90% 时间看的
  │
origin (原图 全分辨率)    ──> 仅用户主动「保存原图」时拉到相册，平时不碰
```

**`thumb` —— 列表场景**

列表一屏往往十几张图，甚至无限滚动。原图动辄几 MB，全量加载等于同时开几十个下载，首屏直接卡白。缩略图短边压到 ~200px、质量 70，单张往往只有十几 KB，十几张加起来还不如一张原图大。列表本就是「扫一眼找内容」，清晰度够辨认足矣，根本不需要原图。

**`preview` —— 点开查看场景**

用户点开某张图想认真看看，这时才需要「像样」的清晰度。但认真看 ≠ 要看全分辨率：手机屏本身也就 1080 上下，原图 4000px 的额外像素在屏幕上根本显示不出来，纯属浪费流量。预览图短边 1080px、质量 80，在手机上和原图肉眼几乎无差别，体积却小一个量级。所以「点开看的图」用预览图最划算。

**`origin` —— 仅保存原图到相册**

全分辨率原图什么时候才要？几乎只有一种情况：用户想把这张照片存到自己相册里、之后可能去打印或二次编辑。这种需求是少数人的偶发动作，不该让所有用户默认承担它的流量和缓存成本。所以原图平时不参与展示、不进 LRU 缓存，只有用户明确点「保存原图」时才 `cacheToLocal(origin)` 拉下来写进相册，页面继续显示预览图，用户去相册里看全分辨率即可。

这个分法其实和微信朋友圈一个思路：点开看到的也是压缩后的中等图，底部才给「保存原图」入口，真要全分辨率自己存相册。大部分时间用户只是「看看拍了啥」，没必要一上来就扛几 MB 原图。

> **三档心法**：列表 `thumb` 省流量、查看 `preview` 够清晰、原图 `origin` 按需取。用户 90% 的时间只看前两者，原图的流量和缓存压力都被压到最低。

## 四、本地文件缓存：让图片「秒开」的关键

微信自带的 `<image>` 其实也有内存/磁盘缓存，但**容量不透明、不可控**。我的做法是：**把图片字节自己落盘到 `USER_DATA_PATH` 下的目录，自己写一套 LRU（最近最少使用）淘汰**。

### 4.1 配置

```ts
const LOCAL_CACHE_DIR = `${wx.env.USER_DATA_PATH}/imgcache` // 本地缓存根目录
const LOCAL_CACHE_MAX = 60 * 1024 * 1024                   // 上限 60MB
const LOCAL_CACHE_META = 'imgcache_meta'                    // 元数据存 storage
```

### 4.2 元数据（记每张图的访问时间，用来淘汰）

```ts
interface LocalEntry {
  fileId: string      // cloud:// fileID
  localPath: string   // 本地文件路径
  size: number        // 字节数
  lastAccess: number  // 最近访问时间戳
}
```

元数据用 `wx.setStorageSync` 存（只是个小 JSON，读写快）；图片字节用 `FileSystemManager` 写文件——大块数据千万别塞 storage，会爆。

### 4.3 下载并落盘（顺带做 LRU 淘汰）

```ts
async function cacheToLocal(fileId: string): Promise<string> {
  if (!fileId.startsWith('cloud://')) return ''
  const cached = getLocalCached(fileId)   // 命中直接返回
  if (cached) return cached

  const fileName = hashId(fileId) + '.img' // 用 fileID 哈希当文件名，天然去重
  const localPath = `${LOCAL_CACHE_DIR}/${fileName}`
  fs.mkdirSync(LOCAL_CACHE_DIR, true)

  const dl: any = await wx.cloud.downloadFile({ fileID: fileId })
  const content: ArrayBuffer = fs.readFileSync(dl.tempFilePath) as any
  fs.writeFileSync(localPath, content)     // 落盘

  // 更新元数据 + LRU 淘汰
  const meta = readLocalMeta()
  meta.push({ fileId, localPath, size: content.byteLength, lastAccess: Date.now() })
  let total = meta.reduce((s, m) => s + m.size, 0)
  meta.sort((a, b) => a.lastAccess - b.lastAccess) // 最久未访问排前面
  while (total > LOCAL_CACHE_MAX && meta.length > 0) {
    const oldest = meta.shift()!          // 淘汰最旧的
    total -= oldest.size
    fs.unlinkSync(oldest.localPath)
  }
  writeLocalMeta(meta)
  return localPath
}
```

**LRU 一句话讲清**：每次访问更新 `lastAccess`；写入后若总大小超 60MB，就把最久没看的图从磁盘删掉，直到不超标。

### 4.4 用 fileID 哈希当文件名的好处

`hashId()` 把 `cloud://` 那串长地址哈希成短名，**同一张图永远映射到同一个本地文件**，天然去重，不会重复缓存。

## 五、封装一个图片组件：展示即缓存

这是「秒开」的最后一公里。我封装了一个 `<smart-image>` 组件，把 `cloud://` 的智能解析、分级加载、本地缓存全包进去，业务层只管传图。

组件带 `thumb` / `preview` / `src` 三个尺寸属性，对应第三节出的三档图：列表传 `thumb`（缩略图）、点开查看传 `preview`（预览图）、要原图时才用 `src`（origin）：

```ts
Component({
  properties: {
    src: { type: String, value: '' },        // 原图（用户点保存原图到相册时才拉）
    preview: { type: String, value: '' },     // 预览图（点开查看用）
    thumb: { type: String, value: '' },       // 缩略图（列表用）
  },
  methods: {
    async _init() {
      const showSrc = this.data.thumb || this.data.preview || this.data.src // 按场景优先取小图
      if (!showSrc.startsWith('cloud://')) { this.setData({ displaySrc: showSrc }); return }

      // 1. 先查本地缓存（命中=秒开，无需网络）
      if (this.data.useLocalCache) {
        const local = imageService.getLocalCached(showSrc)
        if (local) { this.setData({ displaySrc: local, status: 'loaded' }); return }
      }

      // 2. 没缓存：先用 cloud:// 让 <image> 运行时解析展示（保证能显示）
      this.setData({ displaySrc: showSrc, status: 'loaded' })
      // 3. 后台预取到本地，下次就秒开
      imageService.cacheToLocal(showSrc).then((localPath) => {
        if (localPath) this.setData({ displaySrc: localPath })
      })
    }
  }
})
```

我的体会：

- 命中本地缓存 → **直接渲染，零网络等待**，这才是真正的「秒看」
- 没命中 → 先用 `cloud://` 让系统兜底显示（不白屏），**后台默默下载落盘**，下次访问即秒开
- 失败自动重试 1 次，本地路径万一失效就回退 `cloud://`
- 三档都走云存储、都拿 `cloud://`，**共用同一套缓存/清理逻辑**，不用引入新机制

列表用法（只给小图，省流量）：

```xml
<smart-image thumb="{{item.thumb}}" preview="{{item.preview}}" src="{{item.origin}}" mode="aspectFill" width="200rpx" height="200rpx" />
```

点开查看大图时，用 `preview` 传给 `wx.previewImage`（不是原图）：

```ts
onPreview(e) {
  wx.previewImage({
    current: e.detail.previewSrc,
    urls: this.data.previews        // 预览压缩图数组
  })
}
```

### 5.1 按需保存原图到相册

`wx.previewImage` 本身不提供「保存原图」按钮，得在预览浮层底部自己加一个。预览图先显示，底部常驻「原图 X MB · 保存原图」，点后才拉 `origin` 并写入用户相册——**原图不替换页面里的预览图显示，用户想细看直接去相册里看就行**，页面该怎样还怎样：

```ts
data: { previewSrc: '', originSrc: '', originSizeMB: 0 }

// 点「保存原图」
async saveOrigin() {
  wx.showLoading({ title: '原图保存中' })
  const local = await imageService.cacheToLocal(this.data.originSrc).catch(() => '')
  wx.hideLoading()
  if (!local) { wx.showToast({ title: '保存失败', icon: 'none' }); return }
  // 落盘到本地后写入相册（需先 wx.authorize 拿到相册权限）
  await wx.saveImageToPhotosAlbum({ filePath: local })
  wx.showToast({ title: '已保存到相册' })
}
```

要点：

- **默认只看 `preview`**，原图字节不下载、不占缓存额度
- 用户点保存 → 才 `cacheToLocal(origin)` 拉原图，落盘后 `saveImageToPhotosAlbum` 写进相册；页面继续显示预览图，不替换
- 原图体积可以在列表数据里带 `originSizeMB`，按钮上显示「原图 X MB」，和朋友圈一致
- 拉取或写相册失败 → 提示失败并回退 `preview` 继续显示，不白屏

## 六、智能预加载：让「下一屏」提前就绪

光在组件里缓存还不够——用户滑到相册那一瞬间才下载，第一眼还是慢。我的解法是：**进入列表/相册页时，一口气把可见+下一屏的图先预载进缓存**。

```ts
// 进相册页时
imageService.prefetch(allFileIds).catch(() => {})

async function prefetch(fileIds: string[]): Promise<void> {
  const cloudIds = fileIds.filter(id => id && id.startsWith('cloud://'))
  await Promise.all(cloudIds.map(id => cacheToLocal(id).catch(() => '')))
}
```

> 进相册页先把全部 fileID 预载一遍，用户滚动时图片早已在本地，体验跟原生相册差不多。

## 七、定时清理：超量即淘汰 + 清孤儿文件

### 7.1 容量清理（LRU，写缓存时就触发）

上面 4.3 的 `cacheToLocal` 每次写入后都会检查 `total > LOCAL_CACHE_MAX`，超了就删最旧的。这是**被动清理**，随用随清，不卡 UI。

### 7.2 主动/定时清理的两种思路

小程序**没有后台常驻进程**，不能像服务端那样跑 cron。我试下来两种时机最自然：

**思路 A：冷启动顺手清（推荐）**

在 `app.js` 的 `onLaunch` 里跑一次轻量清理：

```ts
function cleanImageCacheOnLaunch() {
  const meta = readLocalMeta()
  const now = Date.now()
  const EXPIRE = 7 * 24 * 3600 * 1000 // 7 天未访问视为过期
  const expired = meta.filter(m => now - m.lastAccess >= EXPIRE)
  if (expired.length) {
    expired.forEach(m => { try { fs.unlinkSync(m.localPath) } catch {} })
    writeLocalMeta(meta.filter(m => now - m.lastAccess < EXPIRE))
  }
}
```

> 清理就是同步删几个文件，几十张图毫秒级，无感。启动页本来就有加载动画，正好并行做掉。

**思路 B：离开页面时清孤儿文件**

上传了但没最终提交的图片，离开页面时主动清理掉，免得云存储留一堆没人引用的孤儿文件：

```ts
// 离开页面时清理已上传但未提交的图片
imageService.remove(pendingFileIds).catch(() => {})
```

### 7.3 删除即同步清缓存

```ts
async function remove(fileIds: string[]): Promise<void> {
  await wx.cloud.deleteFile({ fileList: fileIds })   // 删云存储
  const meta = readLocalMeta()
  const remaining = meta.filter(m => !fileIds.includes(m.fileId)) // 同步删本地元数据
  if (remaining.length !== meta.length) writeLocalMeta(remaining)
}
```

> 云文件删了、本地缓存元数据也同步删，**两侧一致**，不会出现「云上没了、本地还指着旧路径」的幽灵图。

### 7.4 三档图：缓存与清理一起管

分级加载的三档都是 `cloud://`，各自按 fileID 哈希落盘，**天然分开缓存、互不覆盖**：

- LRU 60MB 红线对三档统一生效；预览图/缩略图体积小，能缓存更多张，列表与查看命中率都更高
- 删图时 `remove([origin, thumb, preview])` 三个 fileID 一起删，杜绝孤儿文件
- 原图体积大，被 LRU 淘汰的概率最高——**正好符合预期**：原图本就是偶尔才看的，腾出空间给常看的预览图更合理

### 7.5 进阶：云函数多尺寸（可选）

客户端生成缩略图依赖用户手机算力，图片量很大时可以在云函数里用图像处理生成多档尺寸（如 200/500/原图），上传时只存原图，展示时按场景拼不同尺寸的 fileID。图片量大的相册类场景值得做，小项目用 3.5 的客户端方案已足够。

## 八、一张图的完整旅程

1. 用户选图 → `upload()` 自动压缩（>1.5MB）→ 上传云存储 → 拿到 `cloud://` fileID
2. 业务只存 fileID（不存临时 URL，会过期）
3. 列表渲染 `<smart-image src="cloud://...">`
4. 首次：组件先用 `cloud://` 兜底显示 → 后台 `cacheToLocal` 下载落盘
5. 再次访问同一图：组件 `getLocalCached` 命中 → **直接读本地文件，秒开**
6. 进相册页：`prefetch` 把全部图预载进缓存
7. 清理触发（超 60MB / 7 天未访问 / 删图）：LRU 淘汰或主动清理

---

## 九、关键参数速查

| 参数 | 值 | 作用 |
| :--- | :--- | :--- |
| 压缩阈值 | 1.5MB | 超过才压缩，省画质 |
| 压缩质量 | 75 | 体积/清晰度平衡 |
| 上传并发 | 2 | 防云开发限流 |
| 本地缓存上限 | 60MB | LRU 淘汰红线 |
| 缓存目录 | `USER_DATA_PATH/imgcache` | 自有可控缓存 |
| 过期时间（建议） | 7 天 | 主动清理阈值 |
| 重试次数 | 1 | 组件加载失败自动重试 |

## 十、避坑清单

- ❌ 业务里散落 `wx.cloud.downloadFile` → ✅ 统一走图片工具函数
- ❌ 展示用临时 URL（会过期）→ ✅ 永远存 `cloud://` fileID
- ❌ 大图原样上传 → ✅ 超阈值压缩
- ❌ 把图片字节塞 `storage`（超限崩溃）→ ✅ 字节落盘，元数据才进 storage
- ❌ 只删云文件不清理本地 → ✅ `remove` 同步清元数据
- ❌ 指望小程序后台定时跑 → ✅ 用启动/离开页面的时机触发清理

## 小结

折腾下来，我的小程序图片方案就是这几招：

1. **上传即压缩**（>1.5MB 压到 75 质量）+ 并发 2 控速
2. **本地文件缓存 LRU**（落盘 `USER_DATA_PATH`，60MB 红线，fileID 哈希去重）
3. **自封装图片组件**（命中缓存零等待，未命中后台预载）
4. **分级加载 + 定时清理**（列表缩略图、查看预览图、原图按需下载；启动/删图触发 LRU 与过期清理）

核心心法就一句：**展示源统一用 `cloud://`，缓存与清理全自己管，不依赖系统黑盒。** 这样无论图多少，用户看到的永远是「秒开」，流量也压得住。

以上是我自己踩坑后摸索出的一套做法，希望能帮到同样在折腾小程序图片的朋友。如果哪天图片量真的大到客户端压缩略图扛不住，再把 7.5 的云函数多尺寸顶上就行。
